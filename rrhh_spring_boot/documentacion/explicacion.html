1 Resumen del Proyecto

Este backend es el núcleo de un sistema de Recursos Humanos (RRHH) MVP, construido sobre Spring Boot 3.3. Expone su API principalmente mediante GraphQL (para consultas y mutaciones de datos), complementado con un módulo REST exclusivo para autenticación JWT.

⚡

Spring Boot 3.3 · Java 17

Framework principal con configuración por perfiles (dev/prod).

🔷

GraphQL (Spring for GraphQL)

API principal. Un único endpoint /graphql para leer y modificar todos los datos.

🐘

PostgreSQL + Flyway

Base de datos relacional. Las migraciones son versionadas automáticamente por Flyway.

🔑

Spring Security + JWT

Autenticación Stateless. Cada request a GraphQL requiere un Bearer Token.

☁️

AWS S3

Almacenamiento en la nube para los reportes de preplanilla generados.

🔔

Firebase FCM

Envío de notificaciones push a dispositivos móviles de los empleados.

2 Flujo de la Aplicación

El ciclo de vida de una petición sigue este orden estricto:

📱Cliente (Postman / App)
→
🛡️Security Filter (JWT)
→
🔷Resolver (GraphQL)
→
⚙️Service (Lógica)
→
🗄️Repository (JPA/DB)

Flujo de Autenticación

  1. Login (POST /api/v1/auth/login) El cliente envía username y password. El filtro de seguridad deja pasar esta ruta sin token.
  2. Generación de tokens AuthService valida las credenciales con AuthenticationManager. Si son correctas, JwtService genera un Access Token (24h) y un Refresh Token (7 días).
  3. Petición autenticada El cliente incluye el Access Token en el header Authorization: Bearer <token> en todas las peticiones a /graphql.
  4. Validación del filtro El filtro JWT intercepta cada petición, valida el token y carga el usuario en el contexto de seguridad de Spring.
  5. Autorización por Rol El Resolver verifica con @PreAuthorize si el usuario tiene el rol requerido (ADMIN, RRHH, SUPERVISOR, EMPLEADO) antes de ejecutar la lógica.

Flujo de Asistencia (IoT)

  1. Enrolar Rostro Un admin usa la mutation enrolarRostro para registrar el codigoFacial de un empleado.
  2. Cambiar estado del sistema Con cambiarEstadoSistema(estado: LECTURA) se pone el dispositivo IoT en modo de marcación.
  3. Marcación de Entrada El dispositivo IoT llama a registrarEntrada enviando el codigoFacial detectado y las coordenadas GPS.
  4. Marcación de Salida Al final del turno, el mismo dispositivo llama a registrarSalida con el código facial.
  5. Generación de Preplanilla Al cierre del período, un admin llama a generarPreplanilla, que calcula días trabajados, faltas, retrasos y genera el reporte en AWS S3.

6 Cómo Probar con Postman — Auth

  1. Crear una nueva Colección En Postman, click en "New Collection" y nómbrala RRHH Backend.
  2. Petición de Login
    • Método: POST
    • URL: http://localhost:8080/api/v1/auth/login
    • Body → raw → JSON:
    { "username": "admin", "password": "password123" }

    Guarda el valor de accessToken de la respuesta.

  3. Configurar el token en la colección Ve a la pestaña Authorization de la colección, selecciona Bearer Token y pega el token obtenido. Todas las sub-peticiones de la colección lo heredarán automáticamente.

7 Cómo Probar con Postman — GraphQL

💡
Postman tiene soporte nativo para GraphQL. Crea una petición de tipo POST y en la pestaña Body selecciona GraphQL. Postman cargará el schema automáticamente si le das la URL del servidor.

Ejemplo 1 — Query: Listar empleados

URL: POST http://localhost:8080/graphql
Body → GraphQL
query ListarEmpleados {
  empleados(page: 0, size: 10) {
    content {
      id
      nombre
      apellido
      cargo { nombre salarioPorHora }
      departamento { nombre }
      estado
    }
    pageInfo {
      totalElements
      totalPages
      hasNext
    }
  }
}

Ejemplo 2 — Mutation: Crear empleado

mutation CrearEmpleado {
  crearEmpleado(input: {
    nombre:           "Juan"
    apellido:         "Pérez"
    fechaContratacion: "2025-01-15"
    departamentoId:   1
    cargoId:          2
    horaEntrada:      "08:00:00"
    horaSalida:       "17:00:00"
    carnetIdentidad:  "0801-1990-12345"
  }) {
    id
    nombre
    apellido
    cargo { nombre }
  }
}

Ejemplo 3 — Mutation: Registrar entrada (IoT)

mutation RegistrarEntrada {
  registrarEntrada(input: {
    codigoFacial: "FACE-001-ABC"
    ubicacionGps: "14.0818,-87.2068"
  }) {
    id
    horaEntrada
    estado
    empleado { nombre apellido }
  }
}

Ejemplo 4 — Mutation: Generar Preplanilla

mutation GenerarPreplanilla {
  generarPreplanilla(
    empleadoId: 3
    periodo:    "2025-05"
  ) {
    id
    periodo
    diasTrabajados
    horasExtra
    faltas
    retrasos
    s3KeyUri
  }
}
⚠️
Si en la respuesta aparece un objeto errors, el tipo de error (FORBIDDEN, NOT_FOUND, BAD_REQUEST) estará en extensions.classification. GraphQL siempre retorna HTTP 200; los errores van dentro del JSON de respuesta.

8 Estructura: Config & Seguridad

Todos los archivos de configuración viven en src/main/java/com/example/rrhh/config/.

⚙️ config/security/SecurityConfig.java Config

Define las reglas de seguridad HTTP. Especifica qué rutas son públicas (/api/v1/auth/**) y cuáles requieren autenticación (/graphql). Registra el filtro JWT y deshabilita CSRF (ya que el sistema es stateless). También configura el AuthenticationManager y el PasswordEncoder (BCrypt).

🔑 config/security/JwtAuthFilter.java Filtro

Intercepta cada request entrante. Extrae el Bearer Token del header Authorization, lo valida usando JwtService, y si es válido carga al usuario en el SecurityContextHolder de Spring para que los @PreAuthorize funcionen correctamente.

🔐 config/security/JwtService.java Servicio

Encapsula toda la lógica de JWT: generación de Access Tokens (usando la clave secreta del .env), generación de Refresh Tokens, extracción de claims (username, roles), y validación de expiración. Usa la librería jjwt.

⚙️ config/graphql/GraphQLScalarConfig.java Config

Registra los escalares personalizados de GraphQL: Date, DateTime, Time y BigDecimal. Sin esta configuración, el schema fallaría al intentar usar esos tipos. Usa la librería graphql-java-extended-scalars.

⚙️ config/cors/CorsConfig.java Config

Configura los orígenes permitidos para peticiones Cross-Origin. Lee los dominios permitidos desde la variable de entorno CORS_ALLOWED_ORIGINS del .env, permitiendo que el frontend (ej. Angular en localhost:4200) consuma la API.

☁️ config/AwsConfig.java Config

Crea el bean del cliente de AWS S3 usando las credenciales del .env. Si AWS_ENABLED=false, esta configuración no activa el cliente S3, por lo que no se necesitan credenciales reales para correr en local.

🔔 config/FirebaseConfig.java Config

Inicializa el SDK de Firebase Admin cargando las credenciales desde el archivo JSON apuntado por FCM_CREDENTIALS_PATH. Si FCM_ENABLED=false, la inicialización es omitida, permitiendo correr sin credenciales Firebase en desarrollo.

9 Estructura: Módulos de Dominio

El dominio de negocio sigue un patrón consistente. Cada módulo contiene: Entity → Repository → Service → Resolver.

🔐 Módulo: usuario/

usuario/Usuario.javaEntity (JPA)

Entidad JPA que implementa UserDetails de Spring Security. Almacena username, contraseña encriptada (BCrypt), estado activo/inactivo y la relación con Empleado. Sus roles se cargan desde la tabla intermedia UsuarioRol.

usuario/auth/AuthController.javaREST Controller

El único controlador REST del sistema. Expone los endpoints de /login, /register y /refresh. Delega completamente la lógica al AuthService.

usuario/UsuarioResolver.javaGraphQL Resolver

Expone las queries usuarios y usuario(id) en GraphQL. También contiene mutations de gestión de cuentas como activarUsuario, desactivarUsuario y asignarRol.

👤 Módulo: proyecto/empleado/

empleado/EmpleadoResolver.javaGraphQL Resolver

Implementa paginación (EmpleadoPage) y protección por rol en cada operación. Utiliza @BatchMapping para resolver el campo usuario de todos los empleados en una sola consulta SQL, evitando el problema N+1 de queries.

empleado/EmpleadoService.javaService

Contiene la lógica de negocio: validaciones al crear/actualizar un empleado (ej. que el supervisor exista y sea de otro departamento), y la construcción de la entidad antes de persistirla.

🏢 Módulos: departamento/ y cargo/

departamento/DepartamentoResolver.java & cargo/CargoResolver.java

Catálogos de la empresa. Exponen los datos de departamentos (con su gerente) y cargos (con su salario base por hora) a través de queries GraphQL. Son la base para crear empleados correctamente.

📅 Módulos: asistencia/ y ausencia/

reconocimientofacial/ReconocimientoFacialResolver.java

Maneja el registro biométrico. La mutation enrolarRostro vincula un codigoFacial (string generado por el hardware IoT) con un empleado. Este código es la clave de identificación para las marcaciones posteriores.

sistemaconfig/SistemaConfigResolver.java

Controla el estado del dispositivo IoT. El enum EstadoSistema (EMPAREJAR, EMPAREJADO, LECTURA, REGISTRADO) determina si el hardware está en modo de enrolamiento de nuevos rostros o en modo de marcación de asistencia.

ausencia/solicitud/SolicitudAusenciaResolver.java

Gestiona el flujo completo de ausencias: creación por parte del empleado, aprobación o rechazo por un supervisor. Cambia el campo estado entre PENDIENTE, APROBADA y RECHAZADA.

💰 Módulo: preplanilla/

preplanilla/PreplanillaService.javaServicio Central

El servicio de mayor peso del sistema. Al ejecutar generarPreplanilla, consulta todos los RegistroAsistencia del empleado en el período indicado, calcula días trabajados, faltas, retrasos y horas extra, construye la entidad Preplanilla y la persiste.

preplanilla/S3Service.java

Se encarga de subir el reporte de preplanilla generado al bucket de AWS S3. Retorna la URI (llave S3) del archivo, que queda guardada en el campo s3KeyUri de la preplanilla. Si AWS está deshabilitado en el .env, esta operación es omitida.

🔔 Módulo: notificacion/ y tokenpush/

notificacion/FcmService.java & tokenpush/TokenPushResolver.java

TokenPushResolver permite a las apps móviles registrar y revocar sus tokens FCM de Firebase. FcmService usa esos tokens para enviar notificaciones push cuando ocurren eventos relevantes (aprobación de ausencias, etc.).

⏰ Módulo: scheduler/

scheduler/SchedulerService.javaTarea Programada

Contiene tareas automáticas que Spring ejecuta de forma programada (usando @Scheduled). Actualmente maneja la lógica de cierre de marcaciones diarias u otras tareas periódicas del sistema.

10 Estructura: Componentes Shared

Componentes reutilizables que sirven a todos los módulos, ubicados en shared/exception/.

shared/exception/GlobalExceptionHandler.java

Contiene DOS manejadores de errores en un solo archivo:
• GlobalExceptionHandler (@RestControllerAdvice): Captura errores en los endpoints REST (/api/v1/auth) y los transforma en respuestas HTTP estándar con ProblemDetail (RFC 7807).
• GraphQLExceptionResolver: Captura errores dentro de los resolvers GraphQL y los transforma en el formato de error estándar de GraphQL ({ errors: [{ message, extensions }] }), mapeando cada tipo de excepción a su código semántico correcto (NOT_FOUND, FORBIDDEN, etc.).

shared/exception/ResourceNotFoundException.java

Excepción de negocio lanzada cuando se busca un recurso por ID y no existe (ej. empleado con ID 999). Se traduce a un error NOT_FOUND en la respuesta.

shared/exception/BusinessException.java

Excepción de negocio para reglas de validación semántica (ej. "El username ya está en uso", "El empleado ya tiene usuario"). Se traduce a error BAD_REQUEST o 422 UNPROCESSABLE_ENTITY.

11 Estructura: Resources

resources/application.ymlConfig Base

Configuración común a todos los entornos. Define la cadena de conexión a la base de datos (leyendo variables del .env), la configuración de Flyway, JPA/Hibernate, el pool de conexiones Hikari, y todos los parámetros de la app (JWT, CORS, AWS, FCM). No contiene valores hardcoded; todo viene de variables de entorno.

resources/application-dev.ymlPerfil DEV

Sobreescribe la configuración base únicamente para desarrollo local. Activa show-sql: true para ver las queries SQL en consola, habilita la interfaz de GraphiQL, y sube el nivel de logs a DEBUG y TRACE para facilitar la depuración.

resources/application-prod.ymlPerfil PROD

Sobreescribe la configuración base para producción. Deshabilita el SQL en consola y GraphiQL por seguridad, aumenta el pool de conexiones para mayor rendimiento y establece todos los logs en WARN para evitar exceso de registros.

resources/graphql/schema.graphqlsContrato GraphQL

El contrato completo de la API GraphQL. Define todos los tipos (Empleado, Preplanilla, etc.), enums, inputs, queries y mutations. Este archivo es la fuente de verdad: si un campo no está aquí, no existe en la API. Los Resolver de Java deben implementar exactamente lo que este schema declare.

resources/db/migration/V1__create_usuario_tables.sqlMigración SQL

Primera migración de Flyway. Crea las tablas del módulo de seguridad: usuarios, roles y usuario_roles. Flyway la ejecuta automáticamente al primer arranque si no ha sido aplicada antes.

resources/db/migration/V2__create_proyecto_tables.sqlMigración SQL

Segunda migración. Crea todas las tablas del dominio de RRHH: departamentos, cargos, empleados, registro_asistencia, solicitudes_ausencia, preplanillas, etc. con sus relaciones (Foreign Keys).

resources/db/migration/V3__insert_seed_data.sqlMigración SQL

Datos iniciales del sistema. Inserta los 4 roles fijos, los tipos de ausencia base, el usuario admin inicial (contraseña: password123), y la configuración inicial del sistema IoT en estado REGISTRADO. Solo se ejecuta una vez.
